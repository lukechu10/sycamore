# Migration Guide: v0.9 to v0.10

> Warning: v0.10 is still currently in active development. Any content below is
> a work in progress and not finalised yet.

## Memos and reducers now return writable signals

`create_memo`, `create_selector`, `create_selector_with`, and `ReadSignal::map`
now return `Signal<T>` instead of `ReadSignal<T>`. Likewise, `create_reducer`
now returns `(Signal<T>, impl Fn(Msg))` instead of
`(ReadSignal<T>, impl Fn(Msg))`. Existing code that only reads these values
usually needs no changes. You can now also use methods such as `.set()` and
`.update()` on the returned signals.

To preserve the previous read-only API, dereference the returned signal. An
explicit `*` is needed where a `ReadSignal<T>` is expected by value, such as a
return type, type annotation, collection element, or component prop:

```rust
// Old
let doubled: ReadSignal<i32> = create_memo(move || count.get() * 2);

// New
let doubled: ReadSignal<i32> = *create_memo(move || count.get() * 2);
```

For component props that accept `ReadSignal<T>`, make the same adjustment:

```rust
let doubled = create_memo(move || count.get() * 2);

// Old
view! { CounterDisplay(value=doubled) }

// New
view! { CounterDisplay(value=*doubled) }
```

Writing to a memo overrides its stored value and notifies dependents; it does
not write back to its sources. The next dependency-triggered recomputation may
overwrite that value:

```rust
let count = create_signal(2);
let doubled = create_memo(move || count.get() * 2);

doubled.set(100);
assert_eq!(doubled.get(), 100);
assert_eq!(count.get(), 2);

count.set(3);
assert_eq!(doubled.get(), 6);
```

For selectors, recomputation compares the new result against the current stored
value, including any manual override. Direct writes use ordinary `Signal`
notification behavior without checking the selector's comparator. In a `batch`,
a pending dependency-triggered recomputation can overwrite a manual write at
batch completion, regardless of the order of the two writes.

For reducers, direct writes notify dependents without invoking the reducer. The
next dispatch applies the reducer to the current state, including any direct
writes:

```rust
let (state, dispatch) = create_reducer(0, |state, delta: i32| state + delta);
state.set(10);
dispatch(2);
assert_eq!(state.get(), 12);
```

## Components and component props

This release contains several changes to how components and component props are
used and defined.

### Implicit props by default

Every component now uses inline props by default. Support for struct props has
been removed. To migrate, either move all fields from your props struct to
function arguments, or pass the entire struct as a single prop instead.

```rust
// Old
#[derive(Props)]
struct FooProps {
    bar: i32
}
#[component]
fn Foo(props: FooProps) -> View { ... }

// Old, with inline props
#[component(inline_props)]
fn Foo(bar: i32) -> View { ... }

// New
#[component]
fn Foo(bar: i32) -> View { ... }
```

### New `#[prop]` attributes

The behavior of `#[prop]` attributes on component props has changed. The
previous behavior was not well documented at all and was an ad-hoc modification
of the [`typed-builder`](https://github.com/idanarye/rust-typed-builder) crate.

The new behavior is intentionally kept simple and adapted to Sycamore's use
case. For more details, see the doc page on the
[`#[component]`](https://docs.rs/sycamore/latest/sycamore/attr.component.html)
proc-macro.

Here is a quick example of the new syntax

```rust
#[component]
fn Foo(
    // Set the default value of the prop if no explicit value is passed.
    #[prop(default = 42)] x: i32,
    // Accept anything that can be converted to a String.
    #[prop(into)] y: String,
    // Option types are optional by default.
    z: Option<i32>
    // This behavior can also be disabled.
    #[prop(required)]
    w: Option<i32>
) -> View { ... }
```

### Components automatically return builders

The `#[component]` function now transforms component functions to return a
fluent-style builder instead of just the raw component function. For users of
the `view!` macro, this shouldn't change anything but for builder API users,
this makes components much nicer to use.

```rust
// Old
#[component(implicit_props)]
fn Foo(bar: i32) -> View { ... }

div().children(
    Foo(FooProps::builder().bar(123).build())
)
// New
#[component]
fn Foo(bar: i32) -> View { ... }

div().children(
    Foo().bar(i32)
)
```

This unifies the syntax between components and built-in elements.

### New syntax for attribute passthrough

The way attribute passthrough is defined for a component has changed to be more
flexible for alternative rendering backends.

```rust
// Old
#[component(implicit_props)]
fn MyButton(#[prop(attributes(html, button))] attributes: Attributes) -> View {
    ...
}

// New
#[component(extend_element!(html:button))]
fn MyButton(attributes: Attributes) -> View {
    ...
}
```

## Interpolated text strings

String literals used as text nodes in `view!` now support reactive interpolation:

```rust
view! {
    p { "Hello, {name}!" }
}
```

Literal braces in text nodes must now be escaped as `{{` and `}}`, just like in
`format!`. For example, change `"{}"` to `"{{}}"`. This also applies to raw string
literals, including inline CSS in `style` elements. String literals used as
attributes or component props are unchanged.

## Explicit reactive attributes and properties

The `view!` macro no longer automatically wraps element attribute or DOM
property expressions in closures. Like component props, expressions are now
passed directly. Use an explicit closure when an expression should update
reactively:

```rust
// Old
view! {
    button(disabled=is_editing.get())
    progress(prop:value=progress.get()[0])
}
// New
view! {
    button(disabled=move || is_editing.get())
    progress(prop:value=move || progress.get()[0])
}
```

This also applies to hyphenated and quoted attributes and `prop:` properties
passed through components, for example
`MyInput(data-count=move || count.get().to_string())`.
Without a closure, a signal read such as `disabled=is_editing.get()` is evaluated
once and will not update, even though it still compiles. Passing a signal directly
where supported (for example `disabled=is_editing`) continues to work.

Child expressions and the DSL's `if`/`match` expressions still automatically
track reactive dependencies. Event handlers, bindings, refs, and attribute
spreads continue to be passed directly.

## Event handlers are now normal methods

Instead of the bespoke `on:event=...` syntax for event handlers, all events
should be attached using `on_event=...` syntax. For example:

```rust
// Old
view! {
    div(on:click=|| { ... })
}
// New
view! {
    div(on_click=|| { ... })
}
```

This change also makes the builder API slightly simpler to use.

```rust
// Old
div().on(event::click, || { ... })
// New
div().on_click(|| { ... })
```
